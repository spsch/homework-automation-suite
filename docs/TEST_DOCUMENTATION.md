# Test documentation

## 1. Scope

| Item                | Value                                                         |
|---------------------|---------------------------------------------------------------|
| System under test   | PrestaShop demo storefront, https://prestashop.tesena.com/cs/ |
| Locale              | Czech (`/cs/`); all UI strings asserted in Czech              |
| Test types          | Smoke (read-only) and end-to-end (creates a customer)         |
| Browsers            | Desktop Chromium, Firefox, WebKit (Playwright devices)        |
| Out of scope        | Checkout/order placement, payment, back office, mobile viewports, other languages/currencies, performance and accessibility audits |

## 2. Test environment and data

- **Shared remote demo shop.** Other people use the same instance, so tests must not
  depend on global state (e.g. stock levels, other customers' data).
- **Customer data** is generated by `createCustomer()` in `tests/support/customer.ts`:
  - e-mail `autotest.<timestamp>.<random>@example.com` (unique per run),
  - first name `Tester`, last name `Auto<6 random letters>` (the shop rejects digits in names),
  - password that satisfies the shop's strength policy, birthday `31.05.1990`.
- One customer is registered **per run** by the `setup` project and stored in
  `playwright/.auth/customer.json` (git-ignored). Accounts are not deleted afterwards
  (there is no storefront way to delete one). Each run leaves one account behind
  (`autotest.*@example.com`).
- Negative registration tests reuse the shop's built-in `demo@prestashop.com` account or
  are blocked by validation, so they never create accounts.
- Test product: **Hummingbird printed t-shirt** (category *Clothes > Men*), variant size **M**,
  colour **Černá**, quantity **2**.

## 3. Execution model

| Project          | Test dir       | Depends on | Notes                                   |
|------------------|----------------|------------|-----------------------------------------|
| `setup`          | `tests/e2e/*.setup.ts` | -  | Chromium, runs once per run             |
| `<browser>-smoke`| `tests/smoke`  | -          | chromium / firefox / webkit             |
| `<browser>-e2e`  | `tests/e2e`    | `setup`    | chromium / firefox / webkit             |

- Timeouts: 60 s per test, 10 s per assertion (remote shop can be slow).
- Local: 4 workers, no retries. CI: 1 worker, 2 retries, `forbidOnly`.
- Artifacts: screenshot + video on failure, trace on first retry, HTML report.
- Tags: `@smoke` and `@e2e` on every test (`--grep @smoke`), in addition to project filters.

## 5. Design decisions

- **Page Object Model + fixtures.** Locators live in `tests/pages/*`; specs receive page
  objects through `tests/fixtures.ts`, so a UI change usually needs a fix in one place only.
- **User-facing locators first** (`getByRole`, accessible names in Czech). Stable CSS/`name`
  attributes are used where the accessible name is ambiguous or missing (password input,
  consent checkboxes, header user block, cart lines).
- **Scoped header locators.** "Odhlásit" also appears in the footer when logged in, so header
  actions are scoped to `#_desktop_user_info`.
- **Registration as a setup project** instead of a `test.describe.serial` chain: each later
  test is independent and retryable on its own, gets the customer through the lazily loaded
  `registeredCustomer` fixture, and is skipped (not failed) if registration breaks.
- **Login through the UI in the cart test** (no stored session) so the flow really uses the
  registered credentials, and so one browser's logout cannot invalidate another's session.
- **Shared cart across browsers.** All browser projects use one customer, and PrestaShop keeps
  one cart per customer, so the cart page may already contain items added by another browser.
  Exact quantities are asserted on the add-to-cart dialog (this test's action). The cart page
  only checks that the line exists with at least that quantity.
- **Waiting for variant AJAX.** Selecting size/colour reloads the product block and
  updates the URL hash. The page object waits for the page `load` event first, because a
  selection made before the theme scripts bind their handlers is silently ignored (seen in Firefox).
- **Smoke never depends on setup**, so a broken registration does not hide storefront health.

## 6. Known issues

| ID    | Area | Description | Handling |
|-------|------|-------------|----------|
| KI-01 | Shop: catalog search | Every search term (incl. exact product names such as "Hummingbird printed t-shirt") returns "Pro tento výraz jsme nic nenašli"; live autocomplete is empty too. Most likely the search index has not been built. Observed 2026-10-27. | SM-07 is marked `test.fail()` with an annotation. It passes while the defect exists and **fails once search is fixed**. Then remove `test.fail()` |
| KI-02 | Test env: WebKit on Windows | Playwright's WebKit build on Windows rejects the shop's TLS certificate (`SSL peer certificate or SSH remote key was not OK`). The chain (Let's Encrypt YE1 → Root YE → ISRG Root X2) is valid: `openssl` verifies it, and Chromium and Firefox accept it. All WebKit tests fail locally on Windows. Not yet verified on Linux CI. | Open. Options: run WebKit only on Linux/macOS, or set `ignoreHTTPSErrors: true` for the WebKit project (this turns off certificate checks, so it is a deliberate decision) |
| KI-03 | Shop data | The *Brown bear printed sweater* tile shows the heading "Hummingbird printed sweater" (image alt and product name differ). | Not asserted. The test product is the t-shirt |
| KI-04 | Test env: shared demo shop | Under heavy parallel load the remote shop occasionally answers slowly, and a page can finish rendering after the 10 s assertion timeout. Firefox also rarely throws an internal `Browser.removeBrowserContext` protocol error when closing a context. | Local workers capped at 4. CI uses 1 worker + 2 retries |

## 7. Adding tests

1. Add or extend a page object in `tests/pages/` and register it in `tests/fixtures.ts`
   if it is new.
2. Put read-only checks in `tests/smoke/` (tag `@smoke`). Put flows that change data in
   `tests/e2e/` (tag `@e2e`).
3. Need a logged-in customer? Use the `registeredCustomer` fixture. Never hard-code credentials.
4. Never assert on global shop state that other users can change (stock, other carts).
